# Cash POS System

Десктопная кассовая система на JavaFX, Spring Boot и SQLite. Приложение поддерживает продажи, возвраты, отложенные чеки, кассовые смены, наличную и безналичную оплату, быстрые товары и синхронизацию с внешними системами.

## Технологии

- Java 21;
- JavaFX 21.0.7;
- Spring Boot 3.5.16;
- Spring Data JPA и Hibernate;
- SQLite (файловая БД, отдельный сервер не нужен);
- Flyway;
- MapStruct и Lombok;
- JUnit 5, AssertJ, Mockito и `MockRestServiceServer`;
- JaCoCo (отчёт о покрытии тестами);
- Maven Wrapper;
- `jpackage` и `jlink` для Windows EXE с урезанным Java-рантаймом.

## Требования для разработки

- Windows 10/11 x64;
- JDK 21, переменная `JAVA_HOME` должна указывать на JDK 21;
- WiX Toolset 3.x для формирования Windows EXE, каталог `bin` WiX должен быть в `PATH`
  (по умолчанию `C:\Program Files (x86)\WiX Toolset v3.11\bin`);
- подключение к интернету при первом запуске Maven для загрузки зависимостей.

Проверка окружения:

```powershell
java -version
.\mvnw.cmd -version
where.exe jpackage
where.exe candle.exe
where.exe light.exe
```

Именно вывод `mvnw.cmd -version` должен показывать Java 21: Java-рантайм, который попадает в
установщик, собирается из того JDK, на котором запущен Maven. Если `JAVA_HOME` указывает на другую
версию, переопределите его на время сессии:

```powershell
$env:JAVA_HOME = "C:\Program Files\Java\jdk-21"
$env:Path = "$env:JAVA_HOME\bin;C:\Program Files (x86)\WiX Toolset v3.11\bin;$env:Path"
```

## Настройка базы данных

Отдельно ставить и настраивать ничего не нужно — БД в `src/main/resources/application.yml` задана как файл SQLite рядом с приложением:

```yaml
spring:
  datasource:
    url: jdbc:sqlite:cash_store.db?foreign_keys=on&journal_mode=WAL&busy_timeout=5000
```

При первом запуске Flyway создаёт файл `cash_store.db` и применяет миграции из `src/main/resources/db/migration`.

Файл БД, файл блокировки `cash-store.lock` и каталог `logs/` создаются при запуске и перечислены в
`.gitignore` — в репозиторий (и в merge request) они не попадают. В БД лежат продажи, пользователи
и пароли доступа к внешним сервисам, поэтому коммитить её нельзя.

Подробности: [настройка БД](docs/DB_SETUP.md).

## Запуск проекта

Запуск из Maven:

```powershell
.\mvnw.cmd spring-boot:run
```

Для JavaFX-разработки также настроен плагин:

```powershell
.\mvnw.cmd javafx:run
```

Главный JavaFX-класс — `kz.store.cash.MainCashApplication`, Spring Boot-конфигурация начинается с `kz.store.cash.CashApplication`.

## Тестирование

Запуск всех тестов:

```powershell
.\mvnw.cmd clean test
```

Запуск одного класса:

```powershell
.\mvnw.cmd -Dtest=PaymentReceiptServiceTest test
```

Запуск одного тестового метода:

```powershell
.\mvnw.cmd -Dtest=PaymentReceiptServiceTest#createsAndDeletesDeferredReceipt test
```

Тесты разделены на четыре уровня:

- **Юнит-тесты сервисов** (`service/*Test`) изолированы от БД и внешних серверов: зависимости
  заменяются Mockito-моками. Они проверяют логику вызовов и ветвления.
- **Юнит-тесты мапперов** (`mapper/*Test`) берут настоящие MapStruct-мапперы без Spring-контекста.
- **HTTP-тесты** (`config/DiaryApiHttpFlowTest`, `service/SyncWith1CTest`) собирают настоящие
  `RestClient` с боевыми обработчиками статусов, настоящие `DebtDiaryExecutor`, `DiaryDebtAuthService`
  и `TokenHolder`; сам HTTP подменён `MockRestServiceServer`. Проверяют авторизацию, повтор после
  401/403, ошибки 4xx/5xx, разбор ответов и тело запросов.
- **Интеграционные тесты на SQLite** поднимают настоящий Spring-контекст на временном файле
  SQLite с реальными Flyway-миграциями, Hibernate и транзакциями:
  `SqliteSchemaIntegrationTest` проверяет схему, `CashFlowSqliteIntegrationTest` — денежные потоки
  (продажа, возврат, долг, отложенные чеки, закрытие смены с SQL-агрегатами, откат транзакций,
  синхронизация 1С, пользователи и настройки). Печать смены в них подменена, остальное боевое.

Если тест падает, Maven не переходит к упаковке приложения.

### Покрытие тестами

JaCoCo подключён в `pom.xml` и работает в обычном `mvn test`; отдельная команда не нужна. После
прогона откройте отчёт:

```text
target/site/jacoco/index.html
```

Цифры по классам лежат в `target/site/jacoco/jacoco.csv`. Общий процент занижен тем, что
JavaFX-контроллеры, диалоги и компоненты (`fx.*`) тестами не покрыты: для них нужен TestFX и
графическая среда. Оценивайте покрытие по слоям `service`, `mapper`, `config`, `handler`, `util`.

### Особенности тестов на SQLite

- Драйвер SQLite бросает исключения ограничений (`NOT NULL`, `UNIQUE`), которые Spring превращает
  в `JpaSystemException`, а не в `DataIntegrityViolationException`. Ловить нужно с учётом этого.
- Денежные колонки (`numeric(15, 2)`) читаются из SQLite как число; в тестах суммы сравниваются
  через `isEqualByComparingTo`, а не `equals`, чтобы не зависеть от масштаба `BigDecimal`.
- Возвраты хранятся с отрицательными суммами (так их формирует диалог возврата), поэтому
  итоги смены `sumCash`/`sumCard` уже учитывают возвраты.

## Сборка JAR и Windows EXE

Полная проверка и создание нового установщика:

```powershell
.\mvnw.cmd clean verify jpackage:jpackage
```

Последовательность следующая:

1. удаляется старый каталог `target`;
2. компилируется production-код;
3. компилируются и запускаются тесты, строится отчёт JaCoCo;
4. формируется Spring Boot fat-JAR;
5. JAR копируется в `target/app`;
6. `jpackage` собирает урезанный Java-рантайм (`jlink`) из списка модулей в `pom.xml` и формирует
   Windows EXE в `target/dist`.

Результаты:

- `target/app/cash-0.0.1-SNAPSHOT.jar` — исполняемый JAR (около 66 МБ);
- `target/dist/CashStore-SQLite-<версия>.exe` — Windows-установщик (около 110 МБ).

Имя файла образуется из свойств `app.name` и `installer.version` в `pom.xml`. Версия установщика
задаётся там же, перед выпуском новой версии увеличьте её.

В установщик попадает не целый JDK, а рантайм только из нужных модулей (около 59 МБ вместо 315 МБ).
Если новая зависимость начнёт требовать модуль JDK, которого нет в списке `addModules`, установленное
приложение упадёт с `NoClassDefFoundError`/`ServiceConfigurationError` — подробности и список модулей
в [сборке Windows EXE](docs/PACKAGING_WINDOWS.md).

Не используйте `-DskipTests` или `-Dmaven.test.skip=true` для релизной сборки.

Подробная инструкция: [сборка Windows EXE](docs/PACKAGING_WINDOWS.md).

## Архитектура

Основные пакеты:

- `fx.controllers` и `fx.dialog` — JavaFX-контроллеры и диалоги;
- `fx.component` — переиспользуемая UI- и кассовая логика;
- `service` — бизнес-операции;
- `service.diary` — интеграция с книгой задолженности;
- `repository` — доступ к SQLite через Spring Data JPA;
- `mapper` — преобразования MapStruct;
- `model.entity` — JPA-сущности;
- `model` — DTO и модели обмена;
- `config` — Spring- и HTTP-конфигурация;
- `security` — локальная авторизация кассира;
- `handler` — бизнес- и интеграционные исключения.

Типичный поток вызова:

```text
JavaFX Controller -> Service -> Mapper/Repository -> SQLite
                         |
                         +-> RestClient -> внешний сервис
```

Контроллер не должен напрямую обращаться к репозиторию. Транзакционные бизнес-операции должны находиться в сервисном слое.

## Сервисы проекта

### Продажи и чеки

- `ProductService` ищет товары по штрихкоду или названию, получает универсальный товар и обновляет розничную цену.
- `SalesService` сохраняет строки продажи, ищет их по идентификатору и удаляет строки отложенного чека.
- `PaymentReceiptService` создаёт обычные, долговые, возвратные и отложенные чеки; связывает чек с открытой сменой; объединяет отложенный чек; рассчитывает суммы смены.
- `QuickProductService` добавляет или удаляет товар из быстрого доступа и возвращает товары в порядке настройки.

При оплате `PaymentReceiptService` получает открытую смену, преобразует элементы корзины в `Sales`, связывает их с `PaymentReceipt` и сохраняет чек одной транзакцией.

### Кассовые смены

- `CashShiftService` открывает и закрывает смену, регистрирует внесение и изъятие наличных, получает итоговые суммы чеков и отправляет отчёт на печать.

Открыть вторую смену нельзя. Закрытие блокируется, пока существуют необработанные отложенные чеки.

### Пользователи и настройки

- `AuthService` проверяет активность пользователя и пароль, сохраняет текущего пользователя и публикует события входа/выхода.
- `CurrentUserStore` хранит авторизованного пользователя для JavaFX-интерфейса.
- `UserService` создаёт, обновляет, удаляет и ищет пользователей, контролируя уникальность логина.
- `AppSettingService` управляет единственной записью настроек приложения.
- `CategoryService` читает и сохраняет категории товаров.

### Интеграция с 1С

- `SyncWith1C` загружает категории и товары из 1С через настроенный `RestClient` (Basic-авторизация). HTTP-вызов намеренно не обёрнут в транзакцию, чтобы не занимать соединение с БД на время сетевого запроса.
- `OneCSyncWriter` записывает полученные данные в БД одной транзакцией: обновляет существующие записи, создаёт отсутствующие. Это отдельный Spring-бин, иначе `@Transactional` не сработал бы при вызове из `SyncWith1C`. Если запись не удалась, обновления уже существующих товаров откатываются.

Перед синхронизацией в настройках должны быть заданы адреса категорий и товаров, а при необходимости логин и пароль. Товары с неизвестной категорией пропускаются; товары без категории синхронизируются без неё.

### Книга задолженности

- `DiaryDebtAuthService` получает и очищает токен внешнего сервиса;
- `TokenHolder` хранит токен в памяти;
- `DebtDiaryExecutor` выполняет запрос и один раз повторяет его после повторной авторизации при HTTP 401/403/419 (второй отказ подряд возвращается ошибкой, без бесконечного цикла);
- `DiaryDebtCustomerApi` загружает страницу клиентов, поддерживает поиск, сортировку и пагинацию;
- `DiaryTransactionApi` отправляет операции продажи и возврата в книгу задолженности.

Адрес сервиса, логин и пароль берутся из `AppSetting`.

## Основные бизнес-потоки

### Продажа

1. Кассир добавляет товары в корзину.
2. Выбирает способ оплаты.
3. `PaymentReceiptService` создаёт чек и строки продаж.
4. Чек привязывается к открытой смене.
5. После успешного сохранения чек может быть напечатан.

### Отложенный чек

1. Создаётся чек со статусом `PENDING`.
2. Текущая корзина синхронизируется со строками продаж.
3. При повторном открытии чек можно изменить или оплатить.
4. Пустой отложенный чек удаляется.

### Возврат

1. Находится исходный чек.
2. Проверяется доступное для возврата количество.
3. Создаётся возвратный чек со ссылкой на исходный.
4. Возврат связывается с текущей открытой сменой.

### Закрытие смены

1. Проверяется отсутствие отложенных чеков.
2. Суммируются наличные, карта, возвраты и долговые операции.
3. Учитываются внесения и изъятия наличных.
4. Смена закрывается и печатается итоговый отчёт.
